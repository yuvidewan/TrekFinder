1. Executive summary

The proposed app is an offline-first trekking companion built around a distinctive idea: the user brings the map, and the app turns that map into an interactive digital experience without replacing its original visual identity.

The user photographs or imports a map. The app analyses its visual content and builds a digital representation that can include trails, rivers, contour lines, mountains, labels, landmarks, campsites and other map elements. Unlike conventional mapping apps, it should not force every map into a standard cartographic style. A traditional topographic map should still look like a traditional topographic map; an illustrated or cartoon treasure map should retain its colours, textures, symbols and visual theme.

Once the user marks their starting point and the map is calibrated as far as the available information permits, GPS updates the user’s position on the reconstructed map. The app records movement, can show the track already travelled, and keeps the map and trek data on the device so navigation can continue without mobile data.

A calibrated overlay on the original photograph is retained as a failsafe. The primary experience is the reconstructed digital map; the original image remains accessible if the reconstruction is incomplete, uncertain or visually wrong. 3D terrain is a later phase, not a requirement for the first release.

Product thesis: make a user-supplied map usable as a live, offline navigation surface while preserving the map’s own character. The differentiator is not merely GPS tracking; it is style-preserving map digitisation paired with a trustworthy spatial model.

What the product is

  • A cross-platform mobile app for iPhone and Android.
  • A map capture/import, reconstruction, calibration and navigation workflow.
  • An offline-first system whose essential navigation features do not depend on a remote service.
  • A visual reconstruction system with a separate internal representation for geometry, features and coordinates.
  • A 2D-first product with a possible future 3D view.

What the product is not

  • Not simply a camera overlay on a paper map.
  • Not a replacement for all global map providers or a guarantee of turn-by-turn routing on arbitrary maps.
  • Not a promise that every arbitrary image can be reconstructed perfectly without user review.
  • Not a substitute for a compass, proper outdoor preparation or established safety practices.

2. Product vision and principles

Vision statement

A trekker can take the map they already trust, convert it into a digital map that still looks like itself, and see their real-world movement on it—without needing internet access during the trek.

Design principles

PrincipleMeaning for product decisions
Preserve the source identityRetain the map’s palette, texture, typography, symbols, line styles, illustration language and overall composition wherever possible.
Structure beneath the surfaceThe app should understand geometry and feature types independently of how they are drawn.
Offline by defaultThe map, calibration, navigation state and recorded track must be stored locally and remain usable without connectivity.
Calibration before confidenceA location marker should only be as confident as the map’s geographic alignment and GPS conditions allow.
Make uncertainty visibleWhen the app is unsure whether a line is a trail or river, or when georeferencing is weak, it should ask the user or clearly communicate uncertainty.
Keep a fallbackThe original map image and its GPS/track overlay should remain available.
User controlThe user chooses when to create a map, start tracking, stop tracking, export or delete trek data.
Build 2D firstProve reconstruction, calibration, offline tracking and reliability before adding 3D.

The most important architectural separation

The map should have at least two related but separate representations:

  • Visual representation: what the user sees—textures, colours, labels, hand-drawn features, icons and theme.
  • Spatial/semantic representation: the geometry and meaning the app uses—paths, points, polygons, contours, possible elevation values, labels, confidence scores and coordinate transforms.

For example, a river can be stored as a polyline while being rendered as a hand-painted blue ribbon. A trail can be stored as a path while retaining the source map’s dotted red styling. This avoids forcing the internal data model to dictate the visual style.

Product quality hierarchy

  1. Navigation correctness and safety-relevant honesty.
  2. Preservation of the source map’s appearance.
  3. Offline reliability and recoverability.
  4. Usability and speed of the capture-to-navigation workflow.
  5. Advanced visualisation such as 3D.

3. Problem statement and target users

Problem

Trekkers may rely on printed maps, downloaded images, guidebook maps or maps made for a specific trail. Conventional GPS apps usually display their own base map rather than the exact map a trekker has. A photograph of a paper map is easy to carry but does not automatically show the user's live position. Generic map conversion can lose the source map’s visual character, and remote areas may have limited or no data connectivity.

Primary user groups

Representative use cases

  • Photograph a folded paper trail map at the trailhead and use it for a day hike.
  • Import a scanned map from a guidebook, calibrate it and track a multi-day trek.
  • Use a hand-drawn or illustrated map for a themed outdoor activity while retaining its visual style.
  • Review the path already travelled after losing sight of a trail junction.
  • Continue navigating when mobile data disappears.
  • Open the original image when the reconstructed version omits or misclassifies a detail.

4. Core experience and user journeys

Journey A: create a map

  1. Open the app and choose Capture map or Import image/PDF page.
  2. Capture the map under useful lighting, or crop/rotate an imported image.
  3. The app corrects perspective and image distortion where possible, while preserving the untouched original.
  4. The app detects likely text, lines, symbols, regions, labels and visual styles.
  5. The user sees a preview of the reconstructed map and can inspect uncertain elements.
  6. The user confirms the map name, optional notes and whether to store a local copy of the source image.
  7. The app asks for calibration: known coordinates/grid, scale and orientation information, reference points, or a guided best-effort method if the map has no geographic references.
  8. The map is saved locally and can be reopened without internet.

Journey B: start a trek

  1. Open a saved map and select Start trek.
  2. Choose or confirm the starting point on the map.
  3. If calibration is not complete, the app explains what is missing and offers the best available calibration method.
  4. The app checks location permission, GPS availability and estimated location quality.
  5. Tracking starts only after clear user confirmation.
  6. The current position appears on the reconstructed map, and the travelled path is recorded.
  7. The user can switch to the original-image fallback at any time.
Decided (18A.5): during a trek the user can tap “I’m here” on any recognisable feature to add a GPS control point. Calibration improves progressively as they walk; this is how maps without coordinates become usable.

Journey C: finish and review

  1. Tap Finish trek to stop recording.
  2. Show duration, distance travelled, track and any location-quality warnings.
  3. Save the trek locally with the map it used.
  4. Offer export/share options only after the user explicitly chooses them.
  5. Allow the user to rename, archive or delete the trek.

Journey D: reconstruction is incomplete

  • Display the original map image alongside or behind the reconstructed view.
  • Mark uncertain features in a review interface before the user relies on them.
  • Allow corrections such as 'this is a trail', 'this is a river', 'move this landmark' or 'do not include this feature'.
  • Keep corrections local initially; no upload should be required for the map to become usable.
  • Do not silently invent missing paths, labels or terrain.

5. Functional requirements

5.1 Capture and import

  • Support camera capture with framing guidance and a review step.
  • Support importing common image formats; evaluate PDF page import for the initial release or a follow-up.
  • Keep the original source immutable so later reconstruction changes can be compared against it.
  • Support crop, rotate and perspective correction without overwriting the original.
  • Detect blur, glare, low contrast, shadows, folds and incomplete map boundaries; suggest retaking only when materially useful.
  • Handle large images without blocking the interface; show progress and allow cancellation.
Decided (18A.2): MVP accepts JPEG, PNG, HEIC, WebP and a single PDF page. Limits: 100 MB / 60 MP input; working image capped at 8000 px on the long edge; original always kept at full resolution. GeoPDF/GeoTIFF in Phase 2.

5.2 Reconstruction and visual fidelity

  • Produce a digital 2D representation with the source map’s visual language.
  • Preserve colour relationships, textures, labels, iconography, line styles and overall composition.
  • Retain source pixels or textured regions when redrawing would reduce fidelity.
  • Represent detectable features as editable objects beneath the rendered visual surface.
  • Provide confidence or review status for detected features.
  • Support a user correction workflow and preserve corrections across app restarts.
  • Never treat an unverified detected line as a confirmed navigable trail.
Decided (18A.3, 18A.6): MVP reconstruction = rectified source raster as the base layer + OCR labels + colour-segmented trail/water candidates as vector features. Corrections are assisted (confirm/reject, tap-to-trace) with manual drawing as fallback. Full stylised redraw is Phase 2.

5.3 Calibration

  • Offer coordinate-grid or known-coordinate calibration when available.
  • Offer scale and orientation inputs when they are printed on the map.
  • Allow the user to mark multiple reference points and associate them with known geographic positions where possible.
  • Explain that a single start point anchors one position but does not independently establish map scale, rotation and geographic distortion.
  • Store the calibration method, transform, residual/error estimate and confidence.
  • Let the user recalibrate if the initial alignment is visibly wrong.
  • Keep image-space navigation available as a limited fallback when true geographic alignment cannot be established.
Decided (18A.4): calibration status is Good / Approximate / Insufficient with measurable thresholds (Good = 5+ points and a 95% upper error bound ≤ 25 m; revised in v2.1 from Phase 0 evidence). See section 7.3 and 18A.4.

5.4 Navigation and tracking

  • Show the live GPS position and heading where device sensors support it.
  • Record a breadcrumb track with timestamps and location-quality metadata.
  • Calculate distance travelled and elapsed time, with appropriate smoothing and clear distinction between measured and estimated values.
  • Support pause/resume and explicit stop/finish controls.
  • Handle app backgrounding, screen lock, interruptions and process termination as reliably as the platform permits.
  • Show last known position and its age if location updates stop.
  • Indicate poor GPS conditions and avoid implying that the dot is exact.
  • Do not promise turn-by-turn routing unless a trustworthy route graph and route-validation system are separately designed.
Decided (18A.10–18A.12): “While using the app” permission only; sampling every 5 m or 10 s (30 s battery saver); fixes worse than 50 m excluded from distance; north-up default with optional heading-up.

5.5 Original-image failsafe

  • Retain a view of the original source image.
  • Draw the GPS position and recorded track on the original image using the same spatial calibration where valid.
  • Allow quick switching between reconstructed and original views.
  • Clearly indicate when the fallback alignment is approximate or only image-space based.
  • Ensure the fallback is available offline and does not depend on a cloud copy.

5.6 Offline and local management

  • Save map image, reconstruction data, calibration and trek data locally.
  • Allow opening and using a completed map in airplane mode.
  • Persist work progressively so a crash does not discard the entire reconstruction.
  • Provide storage usage, delete-map and delete-trek controls.
  • Support export as an optional user action; no automatic upload is required.
  • Consider encrypted app storage and device backup behaviour during implementation.

6. Map reconstruction: the central technical challenge

The defining technical challenge is not drawing a map-like screen. It is turning an arbitrary visual source into a structured, faithful and useful digital representation. Source maps vary widely: some have clear grids and legends, while others are artistic, low-resolution, folded, handwritten or designed only for visual storytelling.

6.1 Suggested processing pipeline

StagePurposeOutput
1. Preserve sourceStore the untouched input and basic metadata.Original image asset
2. Image preparationCrop, rotate, correct perspective, improve contrast where useful.Working image plus transform history
3. Visual analysisEstimate palette, regions, text blocks, lines, symbols and textures.Image feature candidates
4. Text and symbol detectionRead labels and identify likely map symbols.Labels and symbol candidates with confidence
5. Geometry extractionTrace lines, boundaries, point symbols and contour-like features.Vector candidates
6. Semantic classificationEstimate whether candidates are trails, rivers, contours, boundaries or decorative art.Typed features with confidence
7. Style reconstructionRender extracted features in the original visual style; retain source textures where appropriate.Layered digital map

10. Local packagingPersist everything needed for offline viewing and tracking.Offline map bundle

6.2 Conventional algorithms versus machine learning

A sophisticated program can do a large amount without a generative AI system. Image processing, OCR, connected-component analysis, edge detection, line tracing, colour clustering, geometric transforms and deterministic rendering are useful foundations. Local machine-learning models may help classify difficult symbols or distinguish features when rules are insufficient.

A generative model should not be allowed to invent geographic detail. It might produce a visually plausible but incorrect trail, move a river or alter a label. For a navigation product, plausible-looking errors are especially dangerous. The preferred design is evidence-based extraction plus deterministic rendering, with optional ML assistance and explicit user review.

Decided (18A.1): stages 2–6 run in a shared C++ core built on OpenCV; OCR uses Google ML Kit on-device text recognition. No generative model is used anywhere in the pipeline.

6.3 Style-preserving rendering

  • Maintain a style palette extracted from the source: colours, stroke widths, line patterns, textures and text treatments.
  • Keep a mapping between each digital object and the source region(s) that support it.
  • Use original pixels or image patches as texture layers for complex illustration where vector recreation would be costly or inaccurate.
  • Use vector geometry for features that benefit from interaction, scaling and spatial queries.
  • Use separate visual layers for background texture, terrain art, text, detected features, user annotations, GPS dot and track.
  • Make the GPS marker visually legible without changing the underlying map theme.

6.4 Why a hybrid reconstruction is likely

Pure vector redraw risks losing artistic texture and detail. Pure image overlay does not provide structured, editable features. A hybrid system can preserve complex source art as raster textures while tracing important features into vectors. The app can therefore keep the map’s appearance while making selected objects interactive.

6.5 Confidence and review

Every detected feature should have a status such as candidate, user-confirmed or rejected. Confidence is an engineering aid, not a guarantee of correctness. High-impact features—especially trails, crossings, cliff symbols and junctions—should be reviewable. The app should not make an unverified feature appear more authoritative than the source.

6.6 Limits to acknowledge

  • Low-resolution, blurry or occluded maps may not contain enough detail to extract all features.
  • Legends vary; the same colour or line style can mean different things across maps.
  • Decorative illustrations can resemble geographic features.
  • Hand-drawn maps may not be to scale or geographically accurate.
  • Some maps distort distances intentionally for readability.
  • Text recognition can confuse similar characters or labels.
  • Reconstruction speed and fidelity will depend on map complexity and device capability.

7. Spatial calibration and GPS alignment

Critical constraint: marking the user’s starting point on the map is useful, but one point alone generally cannot determine geographic scale, rotation, projection or distortion. The product must provide additional calibration options or clearly limit what it claims.

7.1 Coordinate spaces

The app should distinguish at least three coordinate spaces:

  • Image space: pixel coordinates in the original photograph or scan.
  • Reconstructed-map space: coordinates used by the digital rendering and its feature geometry.
  • Geographic space: latitude/longitude or an appropriate local coordinate reference used to associate the map with GPS.

A stored transformation links these spaces. It should be possible to transform a GPS location to the corresponding position on the reconstructed map and to the original image for the failsafe.

Decided (18A.4): control points are stored in WGS84, but transforms are fitted in a local tangent plane (east/north metres) centred on the map, never directly in latitude/longitude, which would introduce scale distortion.

7.2 Calibration methods, in preferred order

7.3 Calibration workflow

  1. Ask whether the map has a coordinate grid, scale bar, north arrow or labelled coordinates.
  2. Prefer the simplest reliable method supported by the source.
  3. Where possible, ask for multiple reference points spread across the map rather than clustered together.
  4. Estimate alignment quality and show a simple status such as Good, Approximate or Insufficient data.
  5. Allow the user to preview the GPS marker on the map before starting the trek.
  6. Save the calibration inputs and method so the same map can be reused.
  7. Recalibrate if the user changes the crop or image transform.

Calibration status thresholds NEW

StatusCriteriaApp behaviour
Good≥ 5 control points, hull covering ≥ 15% of the map, 95% upper bound of map-wide error ≤ 25 m.Normal GPS dot with combined uncertainty circle.
Approximate2–4 points (2 = similarity fit; 2–3 = error not measurable), or scale + north + anchor, or error bound 25–100 m.Dot shown with an “Approximate” badge and enlarged uncertainty circle.
InsufficientFewer than 2 points, collinear points, or error bound > 100 m.No geographic dot; track kept, user prompted to add an “I’m here” point.

Displayed uncertainty radius = √(GPS accuracy² + calibration error²). Transform model: 2 points → similarity (scale, rotation, translation); 3+ points → least-squares affine. Higher-order or piecewise models are Phase 2. The error estimate accounts for leverage, so clustered points automatically report large errors far from the cluster. Thresholds were revised in v2.1 from Phase 0 simulation evidence (see 18A.4).

Decided (v2.1, 18A.5): coordinate entry asks for the map’s datum or warns of a possible ~100 m offset; old local datums (e.g. US NAD27, Survey of India Kalianpur) differ from GPS by 86–130 m.

7.4 GPS limitations

  • GPS may work without mobile data, but accuracy varies with terrain, tree cover, weather and device hardware.
  • Mountain walls and narrow valleys can block or reflect satellite signals.
  • GPS noise can make the dot jump or make recorded distance appear longer than actual travel.
  • Compass heading can be unreliable near metal objects or when the user is stationary.
  • The UI should show accuracy radius or quality status where practical, not just a precise-looking dot.
  • Track smoothing should not erase meaningful switchbacks or falsely snap users to an unverified trail.

7.5 What the app can honestly promise

When calibration is strong and GPS conditions are good, the app can show a useful live position on the source map. When either is weak, it should show the uncertainty and keep the original map accessible. It should not claim that a start-point tap alone makes any map geographically accurate.

8.1 Data flow

Capture/import → image preparation → feature extraction → style-preserving reconstruction → user review → calibration → local map package → GPS tracking and rendering. The original image remains attached to the map package throughout.

8.2 Cross-platform strategy

The product must target both iOS and Android. A shared UI and shared core logic may reduce duplicated work, but camera, location permissions, background execution, file import and some image-processing capabilities are platform-specific. The implementation choice should be made after a small technical prototype, not by assuming one framework automatically solves all native requirements.

  • Evaluate a shared cross-platform framework for common UI and product logic.
  • Keep platform-specific adapters for location, camera, permissions, background operation and file access.
  • Benchmark image processing on representative lower-, mid- and high-tier devices.
  • Use the same reconstruction and map-data specification across platforms so a map package has consistent behaviour.
  • Do not commit to a specific stack until performance, plugin reliability and background tracking are tested.
Decided (18A.1) — provisional stack for Phase 0: Flutter UI and renderer; shared C++/OpenCV core via FFI; native location adapters; ML Kit OCR; SQLite. Kill criterion: if Flutter cannot record a 3-hour background track without unexplained gaps on a mid-range Android device, or cannot pan/zoom an 8000 px tiled map smoothly, switch the UI layer to fully native.

8.3 Local processing strategy

The default should be on-device processing. Optional cloud processing, if ever introduced, must be opt-in, clearly explained and never required to navigate. This supports privacy, offline use and predictability. It also means the reconstruction pipeline must be designed to fit device memory, CPU/GPU and thermal limits.

Decided (18A.8): no cloud processing in MVP or Phase 2.

9. Data model and local storage

The data model should preserve source evidence, reconstructed features and geographic alignment independently. The following is conceptual, not a final database schema.

MapFeatureFeature ID, type candidate, geometry, label, confidence, review state, source region, style reference.

Storage principles

  • Keep source image and reconstruction assets linked but independently recoverable.
  • Use a versioned map-package format so future reconstruction improvements do not silently corrupt old maps.
  • Persist track points in batches and recover safely after process termination.
  • Use spatial indexing only where it improves performance; avoid premature complexity.
  • Expose storage usage and allow the user to delete map packages and tracks.
  • Plan for low-storage situations and interrupted imports.
  • Define whether user exports contain raw GPS coordinates and communicate this clearly.

Map package concept

A completed map can be treated as a self-contained local package: source image, corrected working image, rendered layers or textures, feature geometry, style metadata, calibration transform, confidence/review data and optional user notes. It should reopen without needing to rerun every reconstruction stage.

Decided (18A.7): one folder per map containing manifest.json (with format version), source/, working/, tiles/, features.json, style.json and calibration.json. Designed to be zipped as a .trekmap file in Phase 2. Treks and track points live in the app’s SQLite database (WAL mode).

Interaction guidelines

  • Make the first successful map creation achievable without GIS knowledge.
  • Use plain language; explain calibration only when needed.
  • Show reconstruction progress and allow cancellation without losing the original.
  • Distinguish 'map reconstruction complete' from 'geographic calibration complete'.
  • Make the current position visually obvious while preserving the map style.
  • Keep the fallback one tap away during a trek.
  • Use large, high-contrast controls suitable for outdoor use and gloved hands where practical.
  • Prevent accidental trek termination; make pause and finish states clear.
  • Offer a north-up mode and optional heading-up mode if compass quality permits.

Accessibility and outdoor usability

  • Support system text scaling and screen-reader labels.
  • Do not rely on colour alone to distinguish GPS state or feature type.
  • Provide contrast and marker-size options without forcing a complete map restyle.
  • Support dark surroundings and bright daylight through carefully tested contrast choices.
  • Keep critical controls discoverable and avoid tiny touch targets.
  • Consider haptic feedback for tracking start/stop and selected warnings.

11. iOS and Android considerations

iOS

  • Request location permissions in context and explain the benefit before requesting background access.
  • Design for platform-specific background-location behaviour, battery constraints and user-visible indicators.
  • Test screen lock, app switching, calls, low-power modes and force-quit behaviour.
  • Use supported camera/photo-library APIs and handle permission denial gracefully.
  • Test a range of iPhone generations, not only the latest hardware.

Android

  • Account for runtime location permissions, background-location restrictions and foreground-service requirements where applicable.
  • Handle manufacturer-specific battery optimisation that may pause background work.
  • Test varied device vendors, Android versions, memory capacities and screen sizes.
  • Use supported camera and document-picker flows.
  • Make the user-visible tracking state clear where the operating system requires it.
Decided (18A.9, 18A.10): minimum iOS 16 and Android 9 (API 28), arm64, ≥ 3 GB RAM. Only “While using the app” location permission is requested on both platforms; background continuity comes from an Android foreground service of type location started while the app is visible, and iOS background location updates with the system indicator. “Always” permission is never requested.

Shared-platform rule

Cross-platform does not mean platform-identical internals. The user experience and map package should be consistent, but native location services, permissions and background execution must follow each operating system’s current rules. Those details need verification against current platform documentation during implementation.

  • Use incremental processing and checkpoints for large maps.
  • Downsample preview images while retaining original resolution for detail and fallback.
  • Render only visible layers and use caching for expensive textures.
  • Separate high-frequency GPS updates from full map reconstruction.
  • Make location update frequency configurable or adaptive where platform behaviour permits.
  • Do not keep the camera, CPU-intensive image pipeline or unnecessary sensors active during normal tracking.

Reliability and recovery

  • Persist the active trek state and track points regularly.
  • Handle temporary GPS loss without deleting the last known position or track.
  • Show stale-position age and resume updates when available.
  • Keep the original map intact even if reconstruction fails.
  • Validate map package integrity when opening it.
  • Test interruption scenarios: phone call, low battery, app backgrounding, OS termination, device restart and storage exhaustion.

13. Safety, privacy and security

Safety posture

The app supports navigation but cannot guarantee a safe route or a correct position in every environment. A reconstructed map may contain omissions, and GPS can be inaccurate in mountains. The interface should not imply that the app has verified a trail merely because it detected a line in an image.

  • Communicate calibration quality and GPS uncertainty.
  • Keep the source map accessible.
  • Flag unreviewed or low-confidence trail candidates.
  • Do not invent bridges, crossings, safe paths or terrain.
  • Do not present a straight-line connection as a safe route.
  • Encourage users to carry appropriate backup navigation and outdoor safety equipment; do not frame the app as a substitute.

Location permission and background tracking

Background location is sensitive and consumes power. Request it only when the feature genuinely requires it, explain what it enables, and provide a clear way to stop tracking. The product should not require permanent tracking merely to import or view a map.

  • Separate permission to use location while the app is open from any background-tracking permission.
  • Start recording only after the user explicitly starts a trek.
  • Show a persistent, understandable tracking state.
  • Stop collection when the trek ends, subject to clearly explained recovery behaviour.
  • Let users delete saved track history and maps.
  • Never collect or upload location history for analytics by default.

Privacy model

  • Local-first storage should be the default.
  • Do not upload maps, photos or GPS tracks without explicit consent.
  • Keep optional analytics free of precise location data unless a justified, disclosed opt-in is designed.
  • Document how backups, exports and OS-level device backups handle map and track data.
  • Use secure storage practices and appropriate file/database protections.
  • Provide a clear privacy policy before public release.

Security considerations

  • Validate imported file types and handle malformed or unusually large files safely.
  • Limit memory use and guard against crashes from crafted images.
  • Use platform-secure storage options for sensitive metadata where appropriate.
  • Do not expose local files through unintended sharing mechanisms.
  • Keep dependencies updated and review permissions before release.
  • Design exports to be user-initiated and clearly show what data is included.

14. Testing and validation strategy

Build a representative map test corpus

Testing only a few clean topographic maps would create a misleading impression of quality. The corpus should cover a wide range of styles and conditions.

  • High-resolution topographic maps with coordinate grids.
  • Maps with printed scale bars and north arrows.
  • Low-resolution screenshots and compressed images.
  • Photographs with perspective distortion, glare, shadows and folded paper.
  • Illustrated/cartoon maps with non-standard symbols and stylised trails.
  • Hand-drawn maps that may not be to scale.
  • Maps with dense labels, overlapping symbols and multilingual text.
  • Maps with no coordinate references.
  • Maps containing visually similar rivers, roads, trails and contour lines.
  • Maps whose geography is distorted for presentation.
Decided (18A.3): the initial acceptance corpus is ~60 maps in 6 categories of ~10 each: gridded topographic; scale-bar/north-arrow trail maps; guidebook PDF pages; phone photos with glare/folds; illustrated/cartoon maps; hand-drawn sketch maps. Each is annotated with ground-truth trails, labels and, where possible, control points.

Evaluation metrics for reconstruction

  • Visual fidelity: human rating of whether the result preserves source appearance, plus image-based similarity metrics where meaningful.
  • Feature detection precision/recall: measure correct and missed trails, rivers, landmarks and labels against annotated test maps.
  • Geometry error: compare extracted paths and points to annotated reference geometry.
  • Calibration error: measure location alignment error against known reference points, separately from GPS error.
  • Task completion: percentage of users who can create a usable map and start tracking.
  • Correction effort: time and number of edits required before a map is trusted by the user.

Evaluation caution

A map can look visually convincing while being spatially wrong. Visual fidelity and navigation correctness must be measured independently. The app should never use a high style-similarity score as evidence that its coordinates are accurate.

18A. Decision record

Each decision states what was chosen, why, and what evidence would cause it to be revisited. Decisions marked provisional must be confirmed by Phase 0 results.

18A.1 Technology stack (provisional)
Decision: Flutter for UI and rendering; a shared C++ core using OpenCV, called through dart:ffi, for image processing, reconstruction and spatial maths; native location adapters (Kotlin on Android, Swift on iOS) behind platform channels; Google ML Kit on-device text recognition for OCR; SQLite for app data. Map rendering is a custom tiled canvas, not MapLibre/Mapbox.
Rationale: Style preservation is the product. Flutter draws every pixel with its own engine, so a map renders identically on both platforms, whereas frameworks that wrap native widgets introduce small differences. Writing the heaviest code once in C++ guarantees identical reconstruction and transform behaviour on both platforms, as section 8.2 requires. Background location is where cross-platform plugins are least reliable, so it is written natively. Standard web-map engines assume geographic tiles in a fixed projection with their own styling; these maps live in image space with their own style, so a custom tiled canvas is simpler and more faithful.
Revisit if: in Phase 0 Flutter cannot record a 3-hour background track without unexplained gaps on a mid-range Android device, or cannot pan/zoom an 8000 px tiled map smoothly. The C++ core and native adapters remain reusable under a fully native UI.
18A.2 Input formats for the first release
Decision: JPEG, PNG, HEIC and WebP from camera or photo library, plus a single page from a PDF, rasterised on import. Input limit 100 MB / 60 MP; working image capped at 8000 px on the long edge; original always retained at full resolution. GeoPDF and GeoTIFF move to Phase 2.
Rationale: guidebook and park maps are very commonly distributed as PDFs, so excluding them would block a core use case. Size caps bound memory on lower-tier devices. GeoPDF/GeoTIFF would provide automatic calibration but serve a specialist audience.
Revisit if: user testing shows a significant share of users bringing georeferenced files, or multi-page PDFs where page selection is not enough.
18A.3 MVP reconstruction scope and quality bar
Decision: MVP reconstruction is a hybrid: the rectified, cleaned source raster as the base layer; OCR-detected labels; and trail/water candidates from colour segmentation and line tracing, stored as vector features and rendered in the source’s colours and line styles. Full stylised redraw is Phase 2. Acceptance bar on the ~60-map corpus: trail-segment recall ≥ 70% and label read accuracy ≥ 80% on clean topographic maps; a first-time user reaches a reviewed, usable map in under 10 minutes.
Rationale: fully automatic redrawing of arbitrary maps is the riskiest part of the plan. Using the source pixels as the base layer means the MVP can never look less like the original than the paper map itself, while the vector layer still provides structure, interactivity and review — this is the hybrid approach of section 6.4 with the riskiest step deferred.
Revisit if: Phase 0 shows the vector extraction is already strong enough to redraw reliably, or conversely falls well below the bar on topographic maps.
18A.4 What counts as sufficient calibration
Decision (revised v2.1 after Phase 0 simulation): transforms are fitted in a local east/north tangent plane in metres centred on the map, never directly in latitude/longitude. 2 control points → similarity transform; 3+ → least-squares affine. The reported calibration error is the 95% upper confidence bound of the map-wide RMS error, estimated from the affine fit’s residuals and the leverage of every map point (needs 4+ points). Good: ≥ 5 points, error bound ≤ 25 m, control-point hull ≥ 15% of the map. Approximate: 2–4 points, scale + north + anchor, or bound 25–100 m. Insufficient: fewer than 2 points, collinear points, or bound > 100 m. Displayed uncertainty = √(GPS accuracy² + calibration error²); when the error is not measurable, 100 m is assumed rather than 0.
Rationale: an affine fit through exactly 3 points is always perfect and so reveals nothing about error. 25 m is roughly typical consumer-GPS accuracy under tree cover, so below it the map is no longer the weakest link. Fitting in latitude/longitude would distort scale away from the equator.
Phase 0 evidence: 10,000 simulated calibrations on 5 maps with exact ground truth (USGS, swisstopo, GSI Japan, OpenTopoMap), with realistic tap and GPS errors and spread or clustered layouts. The v2 rule (leave-one-out RMSE, ≥ 4 points, ≥ 50% hull) failed both ways: realistic well-spread taps cover only 22–37% of a map, so Good was never reached; leave-one-out overstated error ≈ 2× for spread points yet understated it in 89% of clustered cases, the most dangerous ones. The revised rule rated only 4.5% of Goods worse than 25 m (worst 33 m). With 4 points too little evidence remains to judge error, so 4 points can never be Good. Map resolution also bounds accuracy: on coarse maps a few pixels of tap error is tens of metres.
Revisit if: field tests show users routinely misjudge position at these thresholds, or the corpus shows well-made maps systematically exceeding 25 m because of projection effects that need a higher-order model.
18A.5 Maps with no scale or coordinates
Decision: supported through a clearly labelled Sketch mode built on progressive “I’m here” control points: whenever the user reaches a recognisable feature they tap it on the map and the current GPS fix is recorded. 1 point: no position shown (“walk to a landmark you can identify”). 2 points: similarity transform, Approximate. 3+ points: affine, Approximate or Good by the 18A.4 rules.
Rationale: it needs no internet and no GIS knowledge, it improves as the user walks, and it never claims more accuracy than it has. It is also the most broadly useful calibration method for every map type, so it is a primary feature rather than a fallback.
Revisit if: users frequently tap the wrong feature (visible as large residuals), which would call for outlier rejection or confirmation prompts.
Datum note (v2.1): coordinates printed on older maps use local datums, so the same numbers are not where GPS puts them: measured offsets are 86–93 m for US NAD27 sheets and ≈ 120–130 m for Survey of India (Kalianpur 1937) sheets. “I’m here” points are immune because they pair the map with the GPS’s own datum. Grid/coordinate entry must therefore ask for the map’s datum (default WGS84, with common local datums offered) or warn that positions may be ~100 m off. Datum conversions must use explicit parameters: the reference library silently applied no shift for the Indian datum when its grid file was absent.
18A.6 Correction workflow
Decision: both assisted and manual. Assisted: confirm/reject candidates and tap-to-trace, where a tap on a line snaps to and follows connected pixels of the same colour. Manual drawing is the fallback. Mandatory review is limited to high-impact classes: trails, water, crossings and landmarks.
Rationale: tap-to-trace is what turns correction from an hour of drawing into minutes. Limiting review to safety-relevant features keeps effort low without hiding uncertainty where it matters.
Revisit if: usability tests show correction effort above the 10-minute target.
18A.7 Export and map-package portability
Decision: MVP: user-initiated GPX export of tracks through the OS share sheet. Phase 2: whole-map export as a single .trekmap zip. From day one, the map package is a folder with a versioned manifest.json, designed to be zipped.
Rationale: GPX is cheap, interoperable with every outdoor app, and expected by users. Exporting whole maps commits to format stability, so it waits until the format settles, as version 1 suggested.
Revisit if: guide/group-leader users need to hand prepared maps to others before Phase 2.
18A.8 Cloud processing
Decision: none in MVP or Phase 2.
Rationale: preserves the privacy and offline promises; no server to operate or pay for; no account system required.
Revisit if: on-device reconstruction misses performance or quality targets on mid-tier devices. Even then any cloud path is opt-in and never required to navigate.
18A.9 Minimum supported devices
Decision: iOS 16+; Android 9 (API 28)+, arm64, ≥ 3 GB RAM. Benchmark matrix: iPhone SE (2nd gen), iPhone 13, current iPhone; budget Samsung Galaxy A-series, Pixel 7a, current Android flagship.
Rationale: covers the large majority of phones in active use while excluding devices that cannot reliably process an 8000 px working image.
Revisit if: Phase 0 memory profiling shows 3 GB devices failing, or target markets skew to older devices.
18A.10 Location permission level
Decision: request only “While using the app” on both platforms; never request “Always”. Continuity with the screen locked comes from an Android foreground service of type location started while the app is visible (with its persistent notification), and iOS background location updates with the system location indicator.
Rationale: both platforms allow tracking that was started in the foreground to continue in the background under this arrangement. It avoids the most alarming permission prompt, eases app-store review and matches the privacy model in section 13.
Revisit if: current platform rules change, or Phase 0 testing finds track gaps that only “Always” permission resolves. Details must be verified against current platform documentation during implementation.
18A.11 GPS sampling and track persistence
Decision: default 5 m distance filter with a maximum 10 s interval; battery-saver mode 30 s. Fixes with reported accuracy worse than 50 m are kept but flagged and excluded from distance. Track points are written to SQLite (WAL mode) in batches of 10 points or every 30 s. Tracks are never snapped to trails.
Rationale: at walking speed this captures switchbacks without excessive battery drain; batching limits crash loss to roughly 30 seconds of track.
Revisit if: battery measurements over multi-hour sessions exceed acceptable drain, or distance measurements are noticeably inflated by noise.
18A.12 Map orientation
Decision: north-up by default (for sketch maps, “as drawn”); heading-up available as a toggle only when the compass reports good accuracy. The position marker shows a heading cone only when heading is reliable.
Rationale: phone compasses are unreliable when stationary or near metal, and north-up keeps the map looking like the paper the user trusts.
Revisit if: the field usability study shows a strong preference for heading-up.
18A.13 Future 3D direction
Decision: realistic terrain, not illustrated 3D: the user’s map draped over open elevation data (e.g. Copernicus GLO-30), downloaded before the trek, available only for maps with Good calibration.
Rationale: extruding illustrated art into 3D would mean inventing terrain, which violates the product’s core rule. Real elevation data is free and honest.
Revisit if: user research shows strong demand for stylised 3D of illustrated maps, which would need to be presented clearly as decorative.
18A.14 Business model
Decision: free download with up to 2 saved maps and all safety features; one-time “Pro” purchase unlocks unlimited maps, GPX export and Sketch mode with unlimited control points. No subscription unless cloud features are introduced later.
Rationale: with no server costs a subscription is hard to justify, and outdoor users resist subscriptions. Safety-relevant features are never behind the paywall.
Revisit if: ongoing costs appear (cloud sync, reference data licensing) or conversion data argues for a different split.
18A.15 Map copyright
Decision: MVP is personal use only, with no sharing between users. Import screens carry a short notice that the user is responsible for having the right to use the map.
Rationale: without redistribution there is minimal copyright exposure; a sharing policy is a prerequisite for Phase 3 sharing features.
Revisit if: sharing features are scheduled, or legal review advises otherwise.

19. Glossary

Closing summary

The app’s differentiator is the combination of three capabilities: preserve the source map’s visual identity, create a structured digital representation, and align live GPS movement to it while offline. The most credible route to this product is to prove those capabilities in 2D first, retain the original map as a failsafe, and make uncertainty explicit whenever the source map or GPS does not support reliable alignment.

Guiding rule: the reconstructed map should look like the map the user brought, but the app must never confuse visual resemblance with geographic accuracy.
